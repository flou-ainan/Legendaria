# ADR 016 — Project file: `<video>.legendaria.json`

**Status:** accepted (owner approved the next step, 2026-10-27)
**Date:** 2026-10-27
**Related:** ADR-012 (`.ass` + libass), ADR-014 (web editor), plan 07, plan 04 §11.5 (storage format options), `references/openreel_dissection.md` (versioned, validated project file)

## Context

The web editor needs a document to save and reopen: the source video, what was cut, the edited cues and the style. Plan 04 §11.5 listed three options for where edits live:

1. our own JSON;
2. plain `.ass`;
3. an "extended" `.ass` with our data in extra sections or comments.

What the editor must keep that `.ass` cannot hold cleanly:
- **cuts as data**, reversible: a cut must never destroy subtitles, so undoing it brings them back;
- **word timings** (for splitting a cue, snapping, the pop look and future per-word styles);
- **a style name** that maps to a config preset, not a frozen copy of its look.

Extended `.ass` (option 3) is what Inkscape does with SVG. It looks interoperable, but other editors (Aegisub) silently drop unknown sections on save, so round-trips would lose the cuts and the words.

## Decision

- The project is **plain JSON**, saved next to the video as **`<video file name>.legendaria.json`** (`clip.mp4` → `clip.mp4.legendaria.json`).
- Fields (`engine/schemas/project.schema.json`):
  - `"format": "legendaria-project"` and `"version": 1`: checked on load; other values are rejected with a clear error;
  - `source`: the video file name (relative to the project file);
  - `duration`: the source length in seconds;
  - `style`: a style name from the config;
  - `language`;
  - `keep`: the kept `[start, end]` ranges, sorted and not overlapping. Everything else is cut out;
  - `cues`: the cues v1 items (`start`, `end`, `text`, optional `words`).
- **All times are in source time.** Cutting only changes `keep`. `project.remap()` moves the cues onto the output timeline at export time; cues inside a removed part disappear and cues across a cut are clipped (slivers under 80 ms dropped).
- The engine **validates and normalizes** on every load and save (`Project.from_dict`: ranges clipped, merged and sorted; cues sorted; a cue ending before it starts is an error). Saves are atomic (temp file + rename).
- **`.ass`, SRT and VTT are exports**, written from the remapped cues. The editor's live preview is an `.ass` in source time generated by the engine, so the browser (JASSUB) and FFmpeg draw with the same libass and the same file.

## Alternatives considered

- **Plain `.ass` as the project:** interoperable, but it cannot hold reversible cuts or word timings, and its styles would freeze our presets into one file.
- **Extended `.ass`:** keeps interoperability on paper, but other tools drop our data on save, and parsing `.ass` is much more work than JSON.
- **Cues stored in output time:** simpler export, but every cut would rewrite all later cues, and undoing a cut could not bring removed cues back.
- **A project folder or SQLite:** unnecessary for one video and a few thousand cues.

## Consequences

- Hackable: the file is readable JSON with a JSON Schema for editor autocompletion.
- Import of `.ass` / `.srt` into a project stays a separate, pending feature (plan 04 §11.3, item 4).
- A future `version: 2` (several source clips, reordered ranges) needs a migration in `Project.from_dict`; the version check is already in place.
- The kept-range math exists twice, in Python (`project.py`) and TypeScript (`web/src/lib/timeline.ts`). Both have tests with the same cases and a random property test. The server normalizes again on save, so the Python side is the authority.
